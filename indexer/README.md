# ltidx — C++ の参照索引を作る

## 目的

`compile_commands.json` に載っている TU を clang の libtooling(`clang::index`)で解析し、プロジェクト内の参照を 1 行 1 件の TSV に出します。
問い合わせのたびに解析し直す必要がありません。テンプレートの実体化の中の呼び出しも拾います。問い合わせには `../query` の `ltq` を使います(TSV を `rg` で直接引くこともできます)。

設計の背景は `../docs/design.md` を参照してください。

## 前提

- Windows と Visual Studio 2026(18)の C++ ツール。CMake と Ninja は VS 同梱のものを使います
- LLVM の公式配布物 `clang+llvm-<版>-x86_64-pc-windows-msvc.tar.xz` を展開したフォルダ(`include`・`lib`・`bin` が要ります)。動作を確かめた版は 23.1.4 です
  - MSI 版は開発用のライブラリを含まないので使えません

## ビルド

`build.bat` をダブルクリックします。`build\ltidx.exe` ができます(Release、並列 4)。
LLVM の場所は、環境変数 `LLVM_ROOT` か、このフォルダの `llvm-root.txt`(1 行目に展開先のフォルダを書く。git には入りません)で指定します。

```bat
set LLVM_ROOT=D:\llvm\clang+llvm-23.1.4-x86_64-pc-windows-msvc
build.bat
```

`llvm-root.txt` は cmd のコードページ(OEM)で読み書きします。LLVM の場所に日本語などがあり、コンソールのコードページを切り替えている(`chcp 65001`、pwsh のプロファイルで `[Console]::InputEncoding` を UTF-8 にしている など)ときは、`build.bat` が場所を読み違えて `LLVM not found` で止まります。その場合は、上のように環境変数 `LLVM_ROOT` を設定してから叩いてください(`setup.bat` からのビルドは環境変数で場所を渡すので、影響を受けません)。

## テスト

`test\run_test.bat` をダブルクリックします。すべて通れば `PASS` と出ます(Python 3.10 以降が要ります)。

- `test\sample.cpp` を索引にして、`test\expected*.tsv` と比べます。コメント内・無効な `#if` の中・テンプレート内の using 宣言越しの呼び出し・未解決の呼び出しを含みます
- `test\werror.cpp` で、`/WX` 付きの TU が失敗しないことを確かめます
- `test\test_ltidx.py` で、一時フォルダに作った小さなプロジェクトを索引にします。Shift_JIS・UTF-16 のソース、`/source-charset`、仮想関数の上書き、`-update` の結果(共通のヘッダーのテンプレートの実体化・マクロで変わる行を含む)が全体の作り直しと一致すること、行の出どころ(`.own.bin`)が無い・壊れている・別の回のものときは前回の行を残してそう知らせることを確かめます

## 使い方

```bat
ltidx.exe -p <compile_commands.json のあるフォルダ> -root <索引に含めるソースのルート> -o <出力.tsv> [-j 並列数] [-update] [-source-cp コードページ] [-delayed] [-no-inst] [-no-dep] [-no-local] [対象ファイル...]
```

- 優先度を下げて実行するには `start "" /low /wait /b ltidx.exe ...` を使います
- 出力は 5 つです。書き終えてから 5 つまとめて差し替えるので、作っている途中の索引や新旧の混ざった索引を ltq が読むことはありません(ltq などが開いていれば 10 秒まで待ち、それでも開いていれば前の索引を残して終了コード 2 で終わります)。ファイルの更新日時は、解析を始めた時刻にします(解析の途中で変わったファイルも、次の `-update` と ltq が「索引の後に変わった」と扱います)
  - `<出力.tsv>` … `記号 <TAB> 役割 <TAB> 呼び出し元 <TAB> path:line:col <TAB> ソース行`
    - 役割は `def` `decl` `call` `write` `ref` `dep` `override` と、マクロの `macro` `expand` `ifdef` `undef` のどれかです。暗黙の参照は `-implicit` が付きます
    - 仮想関数の呼び出しには、形が付きます(0.5.5 から)。`-dynamic` は限定名の無い呼び出し(`p->f()`・`r.f()`・クラスの中の `f()`。実行時に受け手の型の上書きが動く)、`-static` は限定名つき(`Base::f()`・`Super::f()`。その関数そのものを呼ぶ)です。呼び出しの式(`MemberExpr`、テンプレートの中の `CXXDependentScopeMemberExpr`・`UnresolvedMemberExpr`)の限定名の有無で決めます。clang の `Dynamic` の印は `MemberExpr` にしか付かず、テンプレートの中の `impl_->Advance()` のような呼び出しに付かないためです。式が分からない呼び出しは `Dynamic` の印だけを見ます
    - 呼び出し元は、その参照を含む関数です。関数の中の変数(`static constexpr` の定数など)の宣言の中の参照も、囲む関数にします
    - マクロの行の記号はマクロの名前です。`macro` は `#define`、`expand` は展開、`ifdef` は `#ifdef`・`#ifndef`・`defined()`、`undef` は `#undef` です
      - `expand` は、マクロの名前がファイルに書かれた位置だけに出します(マクロの引数に書かれたものを含む)。別のマクロの本体の中の展開は、使った行に名前が無いので出しません
      - 名前 1 つに置き換えるオブジェクト形式のマクロ(`windows.h` の `#define GetMessage GetMessageW` など)は、3 列目に置き換え後の名前を書きます。ltq は、これで `Mail::GetMessage` の問い合わせに、置き換え後の `Mail::GetMessageW` を答えます
      - マクロで作られた定義・宣言・呼び出し(`Get##name` の貼り合わせ・X マクロなど)は、マクロを使った行に出ます(以前から)
    - `override` は仮想関数の上書きです。記号は上書きするメソッド、3 列目は上書きされる基底のメソッドです(呼び出し元ではありません)。基底のポインタや参照越しの呼び出しは基底のメソッドに解決されるので、ltq がこの行から上書きの関係を辿ります
    - 記号は修飾名で、テンプレート引数は付けません(`Foo<int>::f` は `Foo::f`)
    - `dep` は、テンプレートの中で解決先が決まらない呼び出し・参照です(`t.f()`、`this->f()`、`Base::f()` など)。記号は `?::f` の形で、名前しか分かりません。`-no-dep` を付けると出しません
    - テンプレート内の `using Base::f;` を経由した参照は、clang の索引では using 宣言(`派生::f`)にしか向きません。ltidx は TU の終わりにそのクラステンプレートの実体化を調べ、宣言の先(`基底::f`)の行も `-using` を付けて出します
  - `<出力.tsv>.tu.tsv` … TU ごとの成否・エラー数・秒数・新規行数・最初のエラー・コンパイルのコマンドのハッシュ・ソースを読んだコードページ。**失敗した TU の参照は索引に無い**ので、検索結果の網羅度はここで確かめます
  - `<出力.tsv>.skip.tsv` … `path <TAB> 種類 <TAB> 開始 line:col <TAB> 終了 line:col`。種類は次のどれかです。`ltq` が、テキスト検索の一致が索引に無い理由を答えるのに使います
    - `comment`(コメント)・`inactive`(無効な `#if` の分岐)
    - `dropped` … ファイルに書かれた関数形式のマクロの引数のうち、展開の後のトークンに残らなかった名前の範囲(無効にした assert やログの引数、`#` で文字列にされた・`##` で貼り合わされた名前)。引数に書かれたマクロの名前は除きます
    - `local` … 関数の中の変数・引数と、テンプレートの引数の名前の位置(行にはしません)。ローカル変数 `begin` と `std::vector::begin` のような同じ名前の一致を、ltq が「別の記号」と言うのに使います。`.skip.tsv` は大きくなります(O3DE で 28 MB → 139 MB)。要らなければ `-no-local` で出しません
  - `<出力.tsv>.deps.tsv` … `TU <TAB> path`。TU が読んだルート配下のファイルです。`-update` と、ltq の鮮度の判定に使います
  - `<出力.tsv>.own.bin` … 行の出どころ(バイナリ)。`-update` だけが使います。複数の TU が読むファイルについて、読む TU すべてが出した行を「共通」とし、TU ごとに共通でない行(テンプレートの実体化やマクロで TU ごとに変わる行)のハッシュ(64 ビット)だけを持ちます。大きさは索引の 3% ほどです(実測: 367 TU・索引 40 MB で 1.1 MB)
- `-update` … 前回の索引(同じ `-o`)と比べて、次の TU だけを解析し直して差し替えます。前回の索引は `.deps.tsv` 付き(この版以降)である必要があります
  - 新しい TU、前回失敗した TU、コンパイルのコマンドが変わった TU、前回の後に変わった(消えた)ファイルを読む TU
  - `compile_commands.json` から消えた TU は索引から外します
  - ltidx のオプション(`-root`・`-source-cp`・`-no-dep` など)を変えたときと、出力の形式が変わった ltidx に替えたとき(形式の版をコマンドのハッシュに入れています)は、全 TU を解析し直します
  - 変更を見るのはルート配下のファイルだけです。ルートの外にある生成ヘッダーやサードパーティのヘッダーを変えたときは、全体を作り直してください
  - 前回の行を捨てるのは、変わったファイルと、解析し直す TU か消えた TU だけが読んでいたファイルの行です。ほかの TU も読む、変わっていないヘッダーの行は、残す TU のどれかが前回出した行(`.own.bin` で分かる)だけを残し、解析し直した TU の行を足します。テンプレートの実体化やマクロで生じた行も含めて、全体の作り直しと同じ行になります
  - `.own.bin` が無い・壊れている・同じ回の `.tu.tsv` と組でない(前の版の ltidx で作った索引など)ときは、そう知らせたうえで、共通のヘッダーの前回の行をすべて残します(古い行が残りえます)。この状態は `-update` を付けずに作り直すまで続き、そのたびに知らせます
- 文字コード: UTF-8 として正しくないソースは、cl と同じくコードページで読み、UTF-8 に直して解析します。UTF-16(BOM 付き)も UTF-8 に直します
  - コードページは、TU の `/source-charset:` か `-finput-charset=` があればそれ、無ければ `-source-cp`、それも無ければこの PC の ANSI コードページです(日本語版 Windows なら 932 = Shift_JIS)。`/utf-8` の TU では変換しません(UTF-16 を除く)
  - clang-cl は UTF-8 以外の `/source-charset:` と `/execution-charset:` をエラーにするので、外して解析します
  - 直さないと、Shift_JIS の「表」「ソ」「能」などの 2 バイト目(`\`)が行の継続や文字列のエスケープになり、`//` コメントが次の行を飲んだり TU が失敗したりします
  - 索引の列番号とソース行は、UTF-8 に直した後のものです。ltq も同じ変換をして突き合わせます
- `-delayed` を付けないときは、遅延テンプレート解析を止めます。clang-cl 形式(`cl.exe`・`clang-cl`・`--driver-mode=cl`)の引数には `/Zc:twoPhase` を、gcc 形式(`g++`・`clang++` など)の引数には `-fno-delayed-template-parsing` を足します(MSVC 向けでは、gcc 形式でも既定で遅延します)。これで、一度も実体化されないテンプレート本体の非依存呼び出しも索引に載ります
- 規格は、TU の引数(`/std:`・`-std=`)に従います。C++03 以前の書き方(`register`・`throw()`・`> >` など)も読めます。新しい規格で禁止された書き方(波かっこの中の縮小変換、C++17 での `throw(X)` など)や、今の標準ライブラリに無いもの(`std::bind1st`、C++17 での `std::auto_ptr`)はエラーに数えますが、その TU の行は索引に残ります
  - Windows では、gcc 形式の引数でも標準ライブラリは MSVC のもの(C++14 以降が前提)を読みます。`-std=c++98` などで標準ライブラリを使う TU は失敗し、行が減ります
- 組み込みヘッダー(`<stddef.h>` など)は、`ltidx.exe` の隣に `lib\clang\<版>\include` があればそれを、無ければビルドした LLVM の `lib\clang\<版>` を使います(`-resource-dir` で指定もできます)。配布物(`scripts\get-ltidx.bat` が取ってくるもの)は前者の形で、LLVM 無しで動きます。どちらにも無ければ、解析に進まずに止まります
  - 配布物のライセンス: ltidx.exe は LLVM と clang のライブラリを静的にリンクし、MSVC のランタイムも静的にリンクしています(`/MT`。Release の静的ライブラリは再配布できます)。zip には `LICENSE.txt`(cxxref)、`LICENSE-LLVM.txt`(LLVM のライセンス文。Apache License 2.0 with LLVM Exceptions と旧 LLVM ライセンス)、`THIRD-PARTY-NOTICES.txt`(ltidx.exe に埋め込まれた LLVM の中の別ライセンスの部品。正規表現(BSD 3 条項)・xxHash(BSD 2 条項)・Unicode のデータ。BSD はバイナリで配るときにも表示を求めます)を入れます。組み込みヘッダーは手を加えずに入れていて、各ファイルの冒頭に表示があります。`THIRD-PARTY-NOTICES.txt` は他者の著作権表示なのでリポジトリには置かず、CI が配布物を作るときに、ビルドに使った LLVM の版のタグのソースから `scripts\llvm-notices.py` で作ります(LLVM の版を上げても、取り直しは要りません。表示の場所や形が変わっていれば、CI が失敗します)
- `-no-inst` は比較用です。テンプレートの暗黙の実体化を索引しません
- PCH の指定(`/Yu` `/Yc` `/Fp`)は外して解析します
- 警告をエラーにする指定(`/WX` `-Werror` `-Werror=…`)は外して解析します。cl に無い clang の警告(`override` の付け忘れなど)で TU が失敗扱いになるのを防ぎます

TSV を直接引く例:

```bat
rg "^Circle::update\tcall" index.tsv
rg "\tcall\tmain\t" index.tsv
```

## 制約

- 配布物の LLVM は zlib / zstd を同梱しないため、`zstub.c` で代替しています。`crc32` は zlib と同じ結果を返します。圧縮・展開は常に失敗を返しますが、ltidx は使いません
- 同じ行が複数の TU から出たときは 1 行にまとめます。構成(Debug/Release など)ごとの索引は別々に作り、ltq がまとめて引きます
- `-using` の解決は、その TU にあるクラステンプレートの実体化から引きます。実体化が無いときや、using 宣言が部分特殊化の中にあるときは、using 宣言の行だけが残ります
