# cxxref のベンチマーク

cxxref を入れると、Copilot が C++ の作業をするときに、何が変わるのか、変わらないのかをまとめた資料です。導入するかどうかを決めるために、問題文・渡した指示・エージェントの動き・結果を、悪い結果も含めてそのまま載せます。

- 確度の表記: 【実測】手元で計測した値 / 【公式】一次文書 / 【推測】確かめていないこと
- ここに載せるのは、条件を揃えて測り直した最新の値(2026-11-06〜08)です。それより前の計測(v1〜v12)は、問題の形や指示が cxxref に有利に偏っていたので、ここでは使いません。経緯と古い値は [design.md](design.md) にあります
- 条件の呼び名(A・G・P など)は design.md と同じです

まとめると、cxxref が効くのは「どこで使われているか」に答えれば済む問いで、同じ名前が多く、呼び出しが多くのファイルに散っているときです。呼び出し箇所が分かっても、直すにはそのファイルを開くので、編集の作業では読む量がほとんど減りません。

## 共通の条件

- エージェント: GitHub Copilot CLI(O3DE は 1.0.105、ほかは 1.0.107)。`copilot -p` で 1 問ずつ、毎回新しいセッション
- PC: Windows 11、AMD Ryzen 9 9950X3D(16 コア・論理 32)、メモリ 64 GB
- モデル: gpt-6-luna(Copilot の AI credits。1 AI credit = $0.01【公式: GitHub Docs の billing】)と、Claude Haiku 5.5(Copilot CLI から Anthropic API を直接使う BYOK。従量課金)。どちらも小さく安いモデルで、強いモデルでは測っていません
- 作業フォルダは、毎回同じ状態に戻した写しです(git で戻すか、指紋で確かめる)
- **入力トークン**は、モデルを呼ぶたびに送った入力の合計です。Copilot CLI はモデルを呼ぶたびにそれまでの文脈を全部送り直すので、呼ぶ回数とツールの結果の大きさで決まります。プロンプトのキャッシュから読んだ分も含むので、費用の差は入力トークンの差より小さくなります(AI credits の列を参照)
- **比**(3・4): 問題ごとに、各条件の回の入力の平均どうしの比を出し、それを問題をまたいでまとめたものです。主に幾何平均を載せ、事前の計画で主な指標にした中央値も並べます。括弧の中は 95% の bootstrap 信頼区間で、問題を引き直し、選んだ問題の中で回も引き直したものです(`bench/ratio13.py`)
- **時期による揺れ**: 同じ問題・同じ条件でも、日によって入力が 2〜3 割変わることがありました。そのため、比べるのは同じ時期に交互に流した回どうしだけです

## 1. 呼び出し箇所を挙げる問題(Nox、v13 段階 3)

C++ のゲームエンジン Nox(367 TU)で、関数の呼び出し箇所を挙げさせました。cxxref のほかに、C++ の参照を引ける MCP サーバー 5 つと比べています。

### 問題文(そのまま)

| 問題 | 問題文 | 正解の数 |
|---|---|---|
| T1 | このフォルダは C++ のゲームエンジン Nox のソースです。`nox::reflection::ClassInfo` のメンバー関数 `GetType()` を呼び出している箇所をすべて挙げてください。他のクラスの `GetType()` の呼び出しは含めません。 | 9 |
| T2 | このフォルダは C++ のゲームエンジン Nox のソースです。`nox::JobSystem::Initialize` を呼び出している箇所をすべて挙げてください(定義・宣言は含めません)。 | 15 |
| T3 | このフォルダは C++ のゲームエンジン Nox のソースです。`nox::io::File::Read` を呼び出している箇所をすべて挙げてください(定義・宣言は含めません)。 | 3 |
| T4 | このフォルダは C++ のゲームエンジン Nox のソースです。`nox::detail::IDelegateBase::Reset` を呼び出している箇所をすべて挙げてください。呼び出し先が `IDelegateBase::Reset` であるものが対象で、どの関数の中に書かれているかは問いません。派生クラスで定義された同名の関数 `Reset` を呼んでいる箇所は含めません。定義・宣言も含めません。 | 4 |

問題文の後に、回答の書式([bench/answer-format.md](../bench/answer-format.md))を付けました。問題と正解は [bench/tasks.json](../bench/tasks.json) にあります。T1 は、`/* */` のコメントの中に同じ形の行が 2 つあり、rg で拾うと誤答になる問題です。T4 の呼び出しは、すべて 1 つのヘッダー(`delegate.h`)の中にあります。

この 4 問は、cxxref を作りながら私たちが選んだもので、rg の苦手な形(同じ名前が多い、コメント、テンプレート)に寄っています。cxxref に有利な問題だと考えてください。

### 条件と、渡した指示

- 道具: `view`・`rg`・`grep`・`glob` と、各 MCP サーバーのツールだけ(編集と shell は無し)。モデルは Claude Haiku 5.5、各問 3 回
- どの MCP サーバーにも、同じくらい手厚い使い方の指示を渡しました。最初に呼ぶツールと引数の形、結果の読み方、そのまま答えに使える条件、迷ったときの手、の 4 点です。指示は各ツールの実装を読んで書き、例の名前は問題の対象と重ならないものにしました
  - cxxref(G): [bench/mcp-instructions.md](../bench/mcp-instructions.md)
  - ほかの 5 つ: [bench/ext/](../bench/ext/) の `*-instructions-v13.md`
- 一部の MCP サーバーは、Windows で動かすために手を入れました(`bench/ext/*.patch`)

### 動きの例

モデルを呼ぶ 1 回ごとに、使った道具を 1 行に並べています。`bench/trace13.py` で記録から出し、同じファイルが続くところを「×N」にまとめ、長い区間は(…)で要約しました。道具を使わなかった呼び出し(最後に答えを書く回など)は行に出ません。対象は各問の 1 回目です。

```
T1 を A(rg だけ)で: 27 秒
  1  grep(GetType\s*\()
  2  grep((class_info|_class_info|base|from|dat...) ✗
  3  view(world.cpp) · view(world_legacy.cpp) ×4 · view(database.cpp) ×3 · view(socket_stream_reader.cpp)
     · view(editor_remote_server.cpp) · view(remote_system.cpp) ×3
  4  view(socket_stream_utility.cpp) ×2 · view(socket_stream_writer.cpp)

T1 を G(cxxref)で: 38 秒
  1  refs(nox::reflection::ClassInfo::GetType)
  2  check(11 行) · view(remote_system.cpp)
  3  view(world_legacy.cpp)

T1 を M(clangd-mcp)で: 16 秒
  1  clangd-mcp-find_references · clangd-mcp-find_symbol
  2  view(database.cpp) ×2
  3  view(editor_remote_server.cpp) · view(socket_stream_reader.cpp) · view(world.cpp) · view(world_legacy.cpp)
```

rg だけでは、`GetType(` に一致した行がどのクラスの関数かを決めるため、ファイルを次々に開きます。cxxref は、clang が解決した呼び出しと、索引に入らない一致の理由(「コメントの中」など)を 1 回で返すので、開くファイルが減ります。

```
T4 を A(rg だけ)で: 入力 29,816、15 秒(3 回ともほぼ同じ)
  1  grep(\bReset\s*\() · grep(IDelegateBase)
  2  view(delegate.h)

T4 を G(cxxref)で: 入力 80,773、47 秒(3 回のうち 2 回がこの形。残りの 1 回は refs だけで 16,500)
  1  refs(nox::detail::IDelegateBase::Reset)
  2  grep(Base\s*=|using Base|class .*Delegate|...) · check(4 行)
  3  view(delegate.h) ×3
  4  grep(using Base|void Reset|class IDelegate...)
  5  view(delegate.h)
```

T4 のように答えが 1 つのファイルにまとまっているときは、rg だけのほうが安く済みます。

## 2. 大きなコードベース(O3DE・Unreal Engine 5)

問題の形は 1 と同じ(呼び出し箇所を挙げる)で、A(rg だけ)と G(cxxref + [bench/mcp-instructions.md](../bench/mcp-instructions.md))を比べました【実測】

| | O3DE 2605.0 | Unreal Engine 5.8.4 |
|---|---|---|
| 大きさ | 5,876 TU・29,950 ファイル | 40,181 TU・301,187 ファイル |
| 問題 | 3 問([bench/tasks-o3de.json](../bench/tasks-o3de.json))× 3 回 | 3 問 × 3 回(UE5 のソースは Epic の使用許諾の下にあるので、問題と正解は公開していません) |
| モデル | gpt-6-luna | Claude Haiku 5.5(BYOK) |
| 正答 A → G | 8/9 → 9/9 | 8/9 → 8/9 |
| 入力トークン A → G | 129,291 → 59,121(−54%) | 164,025 → 91,830(−44%) |
| AI credits(1 回) A → G | 0.648 → 0.372 | —(BYOK) |
| 1 回の時間 A → G | 48 秒 → 41 秒 | 61 秒 → 139 秒 |
| 索引づくり | 24 並列で 22 分、メモリ 21.5 GB | 16 並列で 5.1 時間、メモリ 48 GB、ディスク 54 GB |

- 同じ名前が多い問題(O3DE の O1・O3、UE5 の UE3)では、入力が rg だけの 19〜42% になりました。rg だけの側は、変数の型を確かめるためにファイルを何度も開きます
- 例外は UE5 の UE1(`Super::Initialize(Collection)` という同じ形の行が 135 ある問題)で、cxxref のほうが 6% 多くなりました。3 回のうち 1 回で索引の結果が上限を超えて短い形になり、モデルが grep で派生クラスを洗い直したためです
- 修飾名で rg でも絞れる問題(O3DE の O2)では、cxxref の結果が大きく(1 回の実行で約 44,000 文字)、入力が rg だけの 3.6 倍になりました。正答は同じです
- UE5 では、索引の問い合わせが 1 回 1 分前後かかり、時間は rg だけの 2.3 倍でした。その後、MCP サーバーが索引を開いたまま保つようにして、問い合わせは 1 回 19〜33 秒になりました。Copilot での測り直しはまだです
- clangd を使う MCP サーバー 2 つも UE5 で測りました。指示は 1 の手厚いものではなく、その前の版(「grep の前にまずこれを使う」)です。clangd が索引を読み込むのに数分かかり、ほぼ grep で解きました(入力は rg だけの +19%・+28%)。libclang を使う 2 つは、索引づくりが 23 時間・58 時間かかる見込みで、測れませんでした([design.md](design.md) の「ほかの MCP サーバー(UE5)」)

## 3. 普段の作業に近い C++ の問題(Nox、v13 段階 2)

1・2 は「呼び出し箇所を挙げよ」という、索引がいちばん得をする問い方です。そこで、普段頼みそうな作業を、普段の言い方で頼みました。

### 問題の選び方

- 対象の関数は、索引の候補 107 個から乱数(種 13)で選びました(`bench/v13/sample2.py`)。計画は流す前にコミットしました([bench-plan-v13.md](bench-plan-v13.md))。結果を見てから問題を外したことはありません
- 計画との違いが 2 つあります。計画では O3DE の 8 問も流す予定でしたが、採点の構文チェックが 1 問あたり数千 TU に及ぶので、流す前に Nox だけにしました。また、計画で主な指標にしたのは問題ごとの比の中央値ですが、ここでは幾何平均を主に載せ、中央値を並べています
- 問題文は、cxxref の出力を見せずに、別のエージェントに「開発者が Copilot に頼むときの言い方で」書かせました
- 正解は、cxxref の索引を使わずに作りました。宣言と定義に引数を足した中身を clang-cl の構文チェックにかけ、エラーになった呼び出しを正解にしています

<details>
<summary>Q の rule(v0.5.1 から書き直したもの)</summary>

```
# C++ 参照の検索(cxxref)

C++ のリポジトリでは、clang(libtooling)で全 TU を解析した参照索引(リポジトリのルートの `.index`)を、MCP サーバー `code-ref-index` のツールで引けます。

- 使う場面: C++ の関数・型・変数が「どこで使われているか・どこから呼ばれているか」を知る必要があるとき(引数を変える前の呼び出し元の洗い出し、変更の影響の調査、使っている箇所の質問)。このときは、ソースを grep する前に `refs` を呼びます
- 使わない場面: ファイルや関数の説明、場所の分かっている箇所の修正、ログやテストの追加など、使われている場所の一覧が要らない作業。C++ でないリポジトリ
- `refs`(引数 `name` は修飾名か、その末尾)は、1 回で次を返します。各行には、ファイルと行、その行の本文が付きます
  - `calls`: clang が解決した呼び出し。どの関数の中に書かれているか(`[in ...]`)付き。そのまま答えに使えます。同じ名前を rg でソースから取り直して確かめる必要はありません
  - `other references`: 関数ポインターの取得、テンプレート引数などの呼び出し以外の参照
  - `definitions and declarations`: 定義と宣言
  - `unresolved template calls (dep)`: テンプレート内で解決先が決まらない同名の呼び出し。注記とソース行から、呼び出し先を自分で判断してください
  - `text matches ... not in the index`: ソースの同名の一致のうち、索引に無いものとその理由(コメント内・無効な `#if`・マクロ定義・文字列・解析されていないファイル)。「コメント内」とされた一致は答えに含めません
- 呼び出し側を直すときは、`calls` の行の前後だけを開いて直します。直した後の確かめに `refs` を呼び直さないでください(直後は索引の作り直しが裏で走り、結果は前の索引の行を当て直したものです)。確かめは rg で足ります
- `refs` と `check` の引数 `root` には、作業中のフォルダの絶対パスを渡してください(サーバーはプラグインの場所で動くことがあります)
- `check`(引数 `locations` は `path:line` の配列)は、その行が索引でどう扱われているかを返します。rg などで見つけた行を答えに入れるか迷ったときに使います
- 索引が無い(`index not found`)と返ってきたら、そのリポジトリではふだんどおり rg などで探してください。索引の作り方は返ってきたメッセージにあります。作るのは時間がかかるので、作るかどうかはユーザーに確かめてください
```

v0.5.1 の rule は「C++ の呼び出し箇所・参照・定義を探すときは、grep の前にまず `refs`」とだけ書いていて、使わない場面と、直した後に呼び直さないことは書いていませんでした。

</details>

## 計測の限界

- 問題の数が少なく、1 問あたり 3〜5 回です。正答の差は、どの計測でも「差があるとは言えない」程度でした

- 1・2 の問題は、cxxref を作りながら私たちが選んだもので、cxxref に有利な形に寄っています。3・4 は乱数で選び、流す前に計画をコミットしました
