# 作った構成では無効なコードを索引に入れる方法の調査

2026-11-10。試作と計測の記録。試作のスクリプトは `experiments/inactive-flip/`。

**2026-11-11 追記**: 層 1・2a・2b を本体に入れた。下の「本体に入れたもの」を参照。層 3 と「構成を名前で足す」はまだ。

確度の印: 【実測】はこの調査で測ったもの、【推測】は測っていない見込み。

## 何を調べたか

関数の名前や引数を変えるとき、索引を作った構成では無効だった `#if` の中の呼び出しが漏れる。
「すべてのビルド構成で索引を作る」では足りない。理由は 2 つ。

- ビルド構成のどれも定義しないマクロ(外から `-D` で渡すもの、別のコンパイラ・別のプラットフォームのもの)で
  囲まれたコードは、構成を増やしても有効にならない
- 構成ごとに索引を丸ごと作ると、大きさと時間が構成の数だけ増える

そこで、索引の大きさをほとんど増やさずに、無効なコードを拾う方法を重ねて使う形を試した。

## 対象

| | TU | 解析の合計 | 索引 |
|---|---|---|---|
| コードベース A(非公開の C++ コードベース、MSVC) | 367 | 880 秒 | 41.9 MB |
| O3DE(公開のゲームエンジン、Windows・profile・テストなし) | 5,876 | 32,130 秒 | 897 MB |

## 漏れているものの内訳【実測】

### 無効な `#if`

| | 無効な行 | 読んだ行に対して | ファイル |
|---|---|---|---|
| コードベース A | 2,676 | 1.79% | 56 |
| O3DE | 46,705 | 1.47% | 862 |

O3DE の無効な行を、無効にしている条件のマクロの出どころで分けた(`inactive_stats.py`)。

| 出どころ | 行 | 割合 |
|---|---|---|
| どこにも定義が無い(外から渡す・別のコンパイラ・別のプラットフォーム) | 33,940 | 73% |
| ソースの `#define` | 5,013 | 11% |
| `#if 0` | 3,106 | 7% |
| 混在 | 3,068 | 7% |
| コマンドラインの `-D` | 1,535 | 3% |

ビルド構成を切り替えて変わるのは、ほぼ「コマンドラインの `-D`」の 3% だけ。全構成を作っても、無効な行の大半は残る。

### どの TU からも読まれないファイル

`#if` より大きい穴がこちらにあった(`unparsed_stats.py`)。

| | 読まれない .cpp | 読まれた .cpp |
|---|---|---|
| O3DE(build/ を除く) | 1,704 ファイル、513,573 行 | 5,562 ファイル、1,692,428 行 |
| コードベース A(vcpkg_installed を除く) | 227 ファイル、121,278 行(うち 118,633 行は生成物でビルドされない) | — |

O3DE の読まれない .cpp は、パスに tests を含むものが約 465,000 行、別プラットフォーム(android・linux・mac・ios など)が
約 20,000 行、その他が約 29,000 行。テストを切った構成では、無効な `#if`(46,705 行)の約 10 倍のコードが索引の外にある。

### 今の出力での見え方

`AZ::DynamicModuleHandle::Create` を引くと、索引に無い文字列の一致のうち 16 件が「無効な `#if`」に分類され、
compact では 2 件だけが行として出て 14 件はフォルダーごとの件数に畳まれる。16 件の中身は、コメント 12、文字列 1、
別のシンボル 1、本物の呼び出し 2。本物 2 件のうち 1 件は畳まれた側にあった。

## 試した方法

### 層 1: 問い合わせのときに、無効な行を条件つきで 1 行ずつ出す

索引には何も足さない。ltq が無効な範囲の一致を出すときに、その行を囲む `#if` の条件をソースから読んで付ける
(`annotate.py`)。

```
Gems/ImGui/Code/Source/ImGuiManager.cpp:135  [#if defined(LOAD_IMGUI_LIB_DYNAMICALLY) && !defined(AZ_MONOLITHIC_BUILD)]  | m_imgSharedLib = AZ::DynamicModuleHandle::Create(imgGuiLibPath.c_str());
```

名前の一致なので、別のシンボルやコメントも混ざる。下の層で解決できなかった行の受け皿として要る。

### 層 2a: 条件を反転して読み直す

無効だった分岐を制御している行を、写しの中で `#if 1` / `#if 0` / `#elif 1` / `#elif 0` に書き換える(行番号は変えない)。
ltidx の `-overlay` で写しを元のパスに見せ、そのファイルを読む TU を 1 つだけ解析し直す。
得られた行のうち、元は無効だった行のものだけを残す。

- マクロの値は要らない。定義がどこにも無いマクロでも、`#else` の側でも有効にできる
- 元の構成で有効だった親の分岐は書き換えない(インクルードガードを壊さない)。`#if 0` は対象にしない
- 1 回で有効にできない分岐(`#if` / `#elif` の並び)は、パスを重ねる
- 解析にエラーが出ても、得られた行は使う(ltidx はエラーのある TU の行も書く)

結果(`flip_main.py --all`):

| | コードベース A | O3DE |
|---|---|---|
| 対象の行(`#if 0` を除く) | 1,575 | 43,316 |
| 有効にできた行 | 1,533(97%) | 40,241(92.9%) |
| うち識別子のある行 | 604 → 604(100%) | 23,762 → 21,936(92.3%) |
| そのうち索引の行が付いた行 | 412(68%) | 11,724(53%) |
| 足される索引の行 | 1,056 行、171 KB(本体の 0.41%) | 33,397 行、6.4 MB(本体の 0.71%) |
| 解析し直した回数 | 82(エラーあり 27) | 970(エラーあり 306、失敗 0) |
| CPU 時間 | 95 秒(本体の 11%) | 3,450 秒(本体の 10.7%) |
| 実時間 | 18 秒(6 並列) | 227 秒(16 並列) |

「索引の行が付いた行」が 5〜7 割なのは、宣言の続きの行や波かっこだけの行など、もともと行が付かない行を
分母に含むため。正解と突き合わせた適合率は測っていない。

`AZ::DynamicModuleHandle::Create` の本物 2 件での結果:

- `PythonLoader.cpp:50` — `AZ::DynamicModuleHandle::Create` に解決した。ただし種類は `call` でなく `ref`
  (引数のマクロ `IMPLICIT_LOAD_PYTHON_SHARED_LIBRARY` に値が無く、呼び出しとしては組み立てられない)
- `ImGuiManager.cpp:135` — 行が付かなかった。代入先のメンバー `m_imgSharedLib` が、ヘッダーの同じ条件の中で
  宣言されている。.cpp だけを反転してもヘッダーの側は無効なままなので、式が捨てられる
- 別のシンボルだった 1 件(`PipelineLibrary.cpp:261`)は、`AZ::RHI::PipelineLibraryData::Create` と正しく区別できた

### 層 2b: マクロを `-D` で渡して読み直す

反転はファイル 1 つの中だけを変えるので、同じマクロで囲まれた宣言が別のファイルにあると解決できない。
条件が単純なら、そのマクロを TU 全体に `-D` で渡すほうが筋がよい。

`ImGuiManager.cpp` を `-DLOAD_IMGUI_LIB_DYNAMICALLY` を足して解析し直すと、エラー 0 で、135 行目は
`call AZ::DynamicModuleHandle::Create` になり、ヘッダーのメンバーの定義(`ImGuiManager.h:120`)も索引に入った。

この方法が使える範囲を数えた(`dpass_stats.py`)。条件が `defined(X)` か `X` の `&&` だけで、`X` がソースにも
コマンドラインにも定義が無く、`_` で始まる予約名でもないものを対象にした。

| | 無効な行(`#if 0` を除く) | `-D` で有効になる行 | 渡すマクロ |
|---|---|---|---|
| O3DE | 43,599 | 25,624(58.8%) | 369 個 |
| コードベース A | 1,575 | 223(14.2%) | 14 個 |

使えない理由(O3DE、行数): `#elif`・`#else` の分岐 9,977、ほかの TU では定義のあるマクロ 2,882、
コンパイラ・プラットフォームの予約名 2,710、比較や関数形のマクロ 760、`!defined(定義のあるマクロ)` 602、
`#ifndef` 561、`||` を含む 478。これらは反転(2a)で拾う。

全体での計測(行数・大きさ・時間)はしていない。確かめたのは上の 1 件。

### 層 3: 読まれないファイルを、近くの TU のコマンドを借りて解析する

どの TU からも読まれない .cpp を、同じフォルダー(無ければ親をたどる)の TU のコンパイルのコマンドで解析する
(`borrow.py`)。

3 ファイルで確かめた結果: `DynamicModuleHandle_UnixLike.cpp`(エラー 1、`Create` の定義が 197 行目に解決)、
`DynamicModuleHandle_Unimplemented.cpp`(エラーなし)、`Tests/DLL.cpp`(エラー 1、`Create` の呼び出し 6 か所が解決、
フィクスチャの中の 1 か所は拾えず)。

O3DE の読まれない .cpp から 200 ファイルを無作為に選んだ結果(67,822 行):

| | そのまま | 見つからないヘッダーを探して `-I` を足す(`--fix-includes 8`) |
|---|---|---|
| エラーなし | 55 | 65 |
| エラーあり(行は得られた) | 137 | 133 |
| 行が得られない | 8 | 2 |
| 索引の行 | 126,709 行、26.9 MB | 130,823 行、28.0 MB |
| CPU 時間 | 741 秒 | 1,201 秒 |

- 1 行あたりの索引の行は、エラーなしで 3.3〜3.4、エラーありで 0.8 前後。エラーがあると 4 分の 1 しか得られない
- 最初のエラーは 200 件中 86 件が `'AzTest/AzTest.h' file not found`。ヘッダーを探して足すと、今度は 100 件が
  `'gtest/gtest.h' file not found` で止まる。テストを切った構成では gtest のパッケージがディスクに無い
- 全 1,704 ファイルに広げると、索引は約 230 MB(本体の約 26%)、CPU は約 6,300 秒(本体の約 20%)【推測。200 件からの比例】

ヘッダーを探して足す方法は、エラーなしを 10 件増やすのに CPU が 6 割増える。割に合わない。
テストのコードは、テストを有効にした構成を 1 つ足すのが正しい。借用が向くのは、別プラットフォームの実装のように、
ビルドの設定では有効にできないファイル。

## 提案: 重ねて使う

| 層 | 拾うもの | 索引の増え方 | 時間の増え方 | 確かさ |
|---|---|---|---|---|
| 1. 無効な行を条件つきで出す | 無効な `#if` の中の名前の一致すべて | 0 | 問い合わせのときにソースを読むだけ | 名前の一致。別のシンボルも混ざる |
| 2b. マクロを `-D` で渡す | 外から渡すマクロで囲まれたコード(O3DE で無効な行の 59%) | 未計測(2a と同程度の見込み【推測】) | 未計測 | clang が解決。ファイルをまたいで整合する |
| 2a. 条件を反転する | 2b で残る分岐(`#else`、予約名、比較など) | 本体の 0.4〜0.7% | 本体の約 11% | clang が解決。別ファイルの宣言に依存すると落ちる |
| 3. コマンドを借りる | 別プラットフォームの .cpp | 足したコードに比例 | 同左 | エラーなしなら通常どおり。エラーありは部分的 |
| 構成を名前で足す | テストなど、ビルドの設定で切られたファイル | 1 構成ぶん(共通の行は統合される) | 1 構成ぶん | 通常どおり |

2a・2b・3 で得た行は、作った構成の行と区別して持つ(「この条件を仮に有効にして解析した」と分かる印を付ける)。
エラーのある解析から得た行は、`call` が `ref` に落ちることがある。

## 分かっていないこと

- 2a・2b で付いた行の適合率(正解との突き合わせをしていない)
- 2b を全体に回したときの大きさ・時間・エラーの率
- 2a で「有効 0 行」だった 13 ファイルのうち、`#if 0` だけでないもの(`*Module.cpp` の数件)の原因
- 3 で、借りる TU を選ぶ規則(今は最も近いフォルダーの、パスが近いもの)がどこまで妥当か
- 索引の更新(reindex)のときに、どの差分を作り直すか

## 実装するときに直すところ

- ltidx の `.skip.tsv` は、同じ TU の中で 2 回目に読まれたファイル(インクルードガードで全体が飛ぶ)を、
  ファイル全体が無効な範囲として記録する(例: `fmt/format.h inactive 33:1 4412:25`)。試作では「中に索引の行がある
  範囲は捨てる」で避けた
- 無効な範囲の中のコメントは、今は「無効」に数えられる。反転した解析の `.skip.tsv` からコメントの範囲が取れる
- `-Xclang -ivfsoverlay` をコンパイルのコマンドに足しても ltidx は読まない【実測】。差し替えは `Transcoder` の中に入れた
- `docs/design.md` の「コメント・無効な `#if` の中の一致」と「構成の統合」の節

## 本体に入れたもの(2026-11-11)

目的は、ふつうのエージェントが rg で見つける行を、cxxref が見落とさないこと(1 行ずつ出すか、少なくともどのフォルダに
何件あるかを出す)。

- **差分パス**(`scripts/altpass.py`。`index-project` が索引の後に続けて走らせる。`-NoAlt` で止め、前の差分を消す):
  層 2b(条件が単純なら `-D`)と 2a(反転)を、1 ファイルにつき 1 つの TU でまとめて行い、元は無効だった行だけを
  `<索引>.tsv.alt.tsv` に書く。1 回で有効にできない分岐はパスを重ねる(既定 3 回)。`ltidx` の `-overlay` は正式な指定にし、
  エラーがあっても行を書く `-keep-going` を足した
- **ltq と MCP**: 差分の行は `[inactive: #if <条件>]` を付けて、ふつうの行と同じ節に出す。差分で解決できなかった無効な行は、
  これまでどおり文字列の一致として出す(層 1)
- **rg と同じ範囲を読む**: C/C++ でないファイル(スクリプト・ビルドの定義・文書・ほかの言語)の一致を別の節に出す
- **どの行も、どこかに出す**: `--limit` で省いた行、短い形で畳んだ行、並べきれないフォルダを、フォルダごとの件数か、
  上の階層ごとの件数で必ず残す。`--path` にそのフォルダを渡すと 1 行ずつ出る。MCP は、短い形でも上限を超えるときに
  1 節の行数を 60・25・10・5・2 と減らす(末尾で切ると、後ろの節が丸ごと消えるため)
- 短い名前が数百の記号に当たると、`matched symbols:` の 1 行だけで 47 KB になっていた(O3DE の `Activate`)。行の多い順に
  20 個までにした
- **名前を含む行を、全部 1 行ずつ並べる形を足した**(`ltq refs --all`)。件数で残すだけでは、関数の名前を変えるときに
  直す行が分からないため。修飾名で問うたときの、別の記号に解決された行も並べる。どの出力も、最後の行で「名前を含む行の
  うち何行を並べたか」を言う(`== coverage:`)。MCP は、並べきれなかったときにこの一覧を作業ツリーの中の
  隠しフォルダ(`<ルート>\.index\refs` か `<ルート>\.cxxref\refs`)に書いて場所を知らせる。最後の行には、探した範囲も書く。
  開けなかったファイルがあれば、その前の行(`== not searched:`)にパスを出す
- **C/C++ 以外のファイルを、拡張子や大きさで除かない**。rg と同じく中身で見分ける(NUL に当たるまでを探す)。O3DE では、
  バイナリの拡張子の 8,076 ファイルのうち 2,726 がテキスト(Git LFS の実体を取っていないファイル)だった【実測】

O3DE での差分パス【実測】(16 並列、既定の 3 パス・`-D` あり):

| 無効な分岐のあるファイル | 解析できた無効な行 | 差分の行 | 大きさ | 時間 |
|---|---|---|---|---|
| 1,647 | 40,251 / 46,185(87.2%) | 34,421 | 6.6 MB(本体の 0.7%) | 852 秒 |

解析しきれなかった 5,934 行のうち 5,486 行は `miniaudio.h`(1 ファイルに多数のプラットフォームの分岐がある)で、それを除くと
98.3%。`--no-define` やパスの数を変えた比較は、O3DE ではしていない(1 回 14 分)。

rg との突き合わせ(`bench/parity.py`。結果の表は `bench/README.md`)では、コードベース A・O3DE とも、rg の行のうち
どこにも出ないもの(hidden)と全文にも無いもの(missing)が 0【実測】。

残り:

- 層 3(どの TU も読まないファイルを、近くの TU のコマンドで解析する)。今はそのファイルの一致を「read them if they matter」
  として 1 行ずつかフォルダの件数で出すだけ
- テストを有効にした構成を名前で足す(`index-project -Name tests` と CMake の引数で作れる。手順の案内はまだ)
- 差分の行の適合率(正解との突き合わせ)

## 試作の動かし方

`indexer\build.bat` で ltidx を作ってから(`-overlay` が要る)。パスは例。

```
python -I experiments/inactive-flip/inactive_stats.py <ルート> <索引.tsv> <compile_commands.json>
python -I experiments/inactive-flip/dpass_stats.py   <ルート> <索引.tsv> <compile_commands.json>
python -I experiments/inactive-flip/flip_main.py     <ルート> <索引.tsv> <compile_commands.json> <作業フォルダ> --all --passes 4 --jobs 16
python -I experiments/inactive-flip/unparsed_stats.py <ルート> <索引.tsv> <compile_commands.json> build
python -I experiments/inactive-flip/borrow.py        <ルート> <索引.tsv> <compile_commands.json> <作業フォルダ> --sample 200 --jobs 10 --excl build
python -I experiments/inactive-flip/annotate.py      <ルート> <相対パス:行>...
```

`flip_main.py` は、足される行を `<作業フォルダ>/flip-rows.tsv`(パスの番号、索引の行)に書く。
