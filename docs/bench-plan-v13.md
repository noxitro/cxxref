# 計測の計画 v13: 普段の作業に近い条件で、公平に測る(案、2026-11-08)

v12 までの計測は「C++ の呼び出し箇所を漏れなく挙げる」問題に限られ、cxxref に有利な偏りがあった。宣伝に使える主張を確かめるため、次の 3 点を測る。

1. **C++ 以外のプロジェクトでの負担**: プラグインは、C++ でないリポジトリでも有効になる。そこで何も得をしないまま、トークン・時間が増えていないか
2. **普段の作業での効き目**: 呼び出し箇所を挙げさせるのではなく、関数の変更・影響の調査・参照と関係の無い作業を、普段の言い方で頼む
3. **不利な条件での害**: cxxref と食い違う指示や、あいまいな頼み方でも、rg だけより悪くならないか

## これまでの偏りと、この計画での扱い

| これまでの偏り | この計画での扱い |
|---|---|
| 問題の形が「漏れなく `path:line` で挙げ、件数を書く」だけ。索引がいちばん得をする問い方 | 回答の書式を指定しない。変更の作業はビルドが通るか、影響の調査は挙げた箇所の再現率で採点する |
| 問題を、rg が苦手な形(同名が多い・テンプレート・コメント)を選んで作った | 対象の関数を、決めた手順で無作為に選ぶ。乱数の種と候補の一覧を、流す前にコミットする |
| 問題文に、他のクラスの同名の関数を除くなどの細かい条件を書いた | 問題文は、別のエージェントに「開発者が Copilot に頼むときの言い方で」書かせ、cxxref の出力は見せない。素の名前だけの頼み方も入れる |
| cxxref の指示にだけ「rg で取り直す必要はありません」と書き、ほかの MCP には同じ助言が無かった | 製品のまま(rule あり)と、rule なし(道具だけ)を分けて測る。ほかの MCP との比較は、指示をそろえて測り直す(段階 3) |
| 1 回きりの `-p` で、道具を `view`・`rg`・`grep`・`glob` に絞った。1 回目の入力が 4,000〜7,800 トークンと小さい | 道具を絞らない(Copilot CLI の既定の一式。編集と shell も使う)。大きなリポジトリで Copilot が自動で使う索引付きの検索(tgrep)も、そのまま rg だけの側の相手になる |

## 段階 0: モデルを呼ばない計測(済み、2026-11-08)

公開中の v0.5.1 を、`COPILOT_HOME` を分けた Copilot CLI 1.0.107 に入れて測った【実測】

- MCP サーバーは、C++ でないリポジトリでもセッションごとに起動する。`initialize` まで 118〜194 ms
- 索引の無いリポジトリでの `refs` は 1 ms で、684 文字の「索引が無いので rg で探して。作るならユーザーに確かめて」を返す
- 毎回の文脈に入るもの: rule(`cxxref.mdc`、`alwaysApply: true`)2,227 バイトと、ツールの定義 2,186 文字。これまでの計測では、似た大きさの指示とツールの定義で、モデルを呼ぶ 1 回あたり +740 トークン(gpt-6-luna)・+1,230 トークン(Haiku)だった。C++ でないリポジトリでも、この分がかかるはず【推測。段階 1 で測る】

## 段階 1: C++ 以外のプロジェクトでの負担

- リポジトリ(4 つ。どれも公開のもの)
  - Python、TypeScript、C# のプロジェクトを 1 つずつ(中くらいの大きさのもの。候補は流す前に決めてコミットする)
  - C++ だが索引を作っていないリポジトリ(コードベース A の写し。`.index` なし)。rule が refs を呼ばせ、「索引が無い」を受けて rg に戻る分の負担を見る
- 問題(各リポジトリ 3 問): ある関数を使っている箇所を探す、小さな不具合を直す、あるモジュールの働きを説明する
- 条件(2 つ): プラグインなし / プラグインあり(製品のまま)
- 回数: 各 5 回。計 4 × 3 × 2 × 5 = 120 回
- 見るもの: モデルを呼ぶ 1 回あたりの入力の差(1 回目の入力の差)、入力の計の差、refs が呼ばれた回数、作業の成否、最初の応答までの時間と全体の時間、credits

## 段階 2: 普段の作業に近い C++ の問題

- コードベース: コードベース A と O3DE(どちらも公開で、手元で同じ結果を再現できる)。UE5 は使用許諾の都合で問題と正解を公開できず、1 回に時間もかかるので外す
- 問題(各コードベース 8 問、計 16 問)
  - 変更の作業 3 問: 「関数 X に引数を足して、呼び出し側も直して」。対象の関数は、ヘッダーで宣言され、呼び出しが 2 か所以上ある関数から無作為に選ぶ。呼び出し元の名前が他と重なるかどうかで層に分け、コードベースの中の割合に合わせて選ぶ
  - 影響の調査 2 問: 「X の戻り値の意味を変えたい。影響する箇所を調べて」
  - 参照と関係の無い作業 3 問: 説明・ログの追加・テストを 1 つ足す。cxxref が役に立たない作業での負担を見る
- 頼み方: 各問の問題文は、別のエージェントに書かせる(対象の関数と作業の種類だけを渡す)。半分は素の名前だけ(`Initialize` など)、半分は修飾名で書かせる
- 条件(4 つ)
  - A: プラグインなし。既定の道具一式
  - P: プラグインあり(製品のまま。rule あり)
  - M: MCP サーバーだけ(rule なし)。指示の効き目を除いた、道具だけの値
  - X: P に、cxxref と食い違うユーザーの指示を足す(`.github/copilot-instructions.md` に「コードを探すときは rg を使い、見つけた箇所は必ずファイルを開いて確かめること」)。不利な条件でも、A より悪くならないかを見る
- 回数: 各 5 回。計 16 × 4 × 5 = 320 回
- 採点(cxxref の索引は使わない)
  - 変更の作業: 正解は、宣言だけを変えて全体を `clang -fsyntax-only` にかけたときのエラーの位置(直す必要のある呼び出し)。回答の後の写しを同じようにかけ、エラーが 0 件で、変えるべき呼び出しがすべて変わっていれば正答。コードベース A は全 TU(367)、O3DE は正解の TU と変わったファイルを読む TU だけ
  - 影響の調査: 正解の呼び出しのうち、回答が挙げた割合(ファイルと関数の名前で突き合わせる)
  - 参照と関係の無い作業: ビルドが通るか、説明は採点しない(トークンと時間だけを見る)
- 写しは毎回、元の状態に戻す(指紋で確かめる。今の `snapshot.py digest`)

## 段階 3(任意): ほかの MCP サーバーとの比較を、指示をそろえて測り直す

v12 では cxxref の指示にだけ「結果はそのまま使ってよい」とあった。ほかの 5 つにも、それぞれの出力に合わせた同じ程度の指示を書き、コードベース A の 4 問 × 3 回で測り直す。「試した中で唯一トークンを減らせた」と言うなら要る。v12 と同じ Haiku(BYOK、従量課金)か、gpt-6-luna で測るかは、流す前に決める

## 事前の登録と、結果の扱い

- 流す前に、この計画・問題・問題文・採点の台本・主な指標をコミットする。結果を見てから問題を外したり、指標を替えたりしない(問題が壊れていたときだけ、理由を書いて外す)
- 不利な結果も含めて、すべてを design.md と README に書く
- 主な指標

  - 段階 2: 問題ごとに対にした、P と A の入力トークンの比の中央値(95% の bootstrap 信頼区間)と、正答率の差(問題ごとの対で比べる)

## モデル・費用・時間の見込み

- モデルは gpt-6-luna だけ(Copilot の credits)。強いモデルでは測らない。BYOK(従量課金)は使わない(段階 3 で Haiku を選んだときだけ使う)
- これまで gpt-6-luna で流した 451 回で使った credits は計 133(1 回平均 0.30)。変更の作業は往復が増えるので、1 回 0.3〜1.0 credits と見る【推測】
  - 段階 1: 120 回 × 約 0.3 = 約 36 credits
  - 段階 2: 320 回 × 0.3〜1.0 = 約 100〜320 credits
  - 合わせて、これまでの 1〜2.7 倍
- credits が手持ちの枠に収まるかは、流す前に確かめる
- 時間: 1 回 1〜2 分 × 440 回で、順に流して 8〜15 時間。採点の `clang -fsyntax-only` は CPU を使うので、優先度を最低にし、コアを絞って流す。コードベース A の採点は、公開のコードなので GitHub Actions(Windows の実行環境)に移せる
