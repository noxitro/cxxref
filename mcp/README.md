# cxxref の MCP サーバー

## 目的

ltq の問い合わせを、MCP(Model Context Protocol)のツールとして GitHub Copilot に渡します。
CLI 方式(`ltq`)と違って Copilot にシェルを渡す必要が無く、ツールはサーバー名(`code-ref-index`)で承認できます。

| ツール | 内容 |
|---|---|
| `refs` | 記号の呼び出し・参照・定義、仮想関数の上書きの関係、テンプレート内の未解決の同名呼び出し、索引に無いテキスト一致とその理由を 1 回で返す(`ltq refs` と同じ) |
| `check` | `path:line` ごとに、索引の行と、その行を含むコメント・無効な `#if` を返す(`ltq check` と同じ) |

どちらも読み取り専用です。

## 前提

- Python 3.10 以降(標準ライブラリだけを使います。追加のインストールは要りません)
- 対象プロジェクトの索引。`<ルート>\.index\index.tsv` を `..\scripts\index-project.bat` で作ります

## 起動

Copilot が起動するので、手で起動する必要はありません。手で動かすときは次のとおりです(標準入出力で JSON-RPC を話します)。

```bat
code-ref-index-mcp.cmd [--root <ソースのルート>] [--index <索引.tsv>] [--auto-update-wait 秒 | --no-auto-update] [--no-resident] [--max-output-bytes N]
```

- `--root` を省くと、起動されたときのカレントフォルダから親へさかのぼり、`.index` のある最初のフォルダをルートにします(`.git` と同じ探し方)。Copilot CLI は作業フォルダで起動するので、ソースのルートより下で起動しても、ルートの索引を引きます。そのときは出力の先頭に `root: <ルート> (the index is in this parent folder ...)` と出し、パスはルートからの相対で返します。探すのは呼び出しのたびなので、サーバーの起動後に作った索引も拾います
  - ツールの引数 `root`(作業中のフォルダの絶対パス)を渡されたときは、そこからさかのぼって探します
  - プラグインとして起動されると、作業フォルダはプラグインの場所になり、MCP の roots も空です(Copilot CLI 1.0.105 で確かめました)。そのとき(作業フォルダが環境変数 `PLUGIN_ROOT` と同じとき)は、`root` が渡されなければ、Copilot CLI のセッションの記録(`<COPILOT_HOME か ~\.copilot>\session-state\<COPILOT_AGENT_SESSION_ID>\workspace.yaml` の `cwd`)から作業フォルダを取ります。この記録は公開の仕様ではないので、プラグインの rule は `root` を渡すようモデルに指示しています
  - 索引が見つからなければ、索引の作り方(`scripts\index-project.bat` と、ltidx が無ければ `scripts\get-ltidx.bat`)を、このサーバーの隣の絶対パスで添えます
- `--index` を省くと、`<ルート>\.index` の中の索引本体(構成ごとの `<名前>.tsv`)をすべてまとめて引きます
- 環境変数 `CRI_ROOT` と `CRI_INDEX` でも指定できます
- `--auto-update-wait`(既定 10 秒)と `--no-auto-update` は、下の「索引の自動更新」を参照してください。環境変数 `CRI_AUTO_UPDATE_WAIT`・`CRI_AUTO_UPDATE=0` でも指定できます
- `--no-resident` を付けると、下の「呼び出しをまたいで保つもの」を使わず、呼ぶたびにソースと索引を全部読みます(前の版と同じ動き)。環境変数 `CRI_RESIDENT=0` でも指定できます
- `--max-output-bytes`(既定 18,000)は、結果の大きさの上限です。超えると、`refs` は次の順に出し直し、収まった最初のものを返します。どれでも収まらなければ末尾を切って、そう書き添えます。環境変数 `CRI_MAX_OUTPUT_BYTES` でも指定でき、0 で切りません
  1. (仮想関数のとき)全文のまま、上書きの族(`virtual dispatch` の上書きと、上書きへ解決された呼び出し)だけを 10 個までにしたもの(`ltq refs --family 10`)。呼び出し・参照・定義は 1 行も減らしません
  2. 短い形の 1 段目(`ltq refs --compact`)
  3. 短い形の 2 段目(`--compact --compact`。無効な `#if` とマクロの定義の中の一致もフォルダごとの件数にする)
  4. (仮想関数のとき)2 段目で、上書きの族を 5・2 個に減らしたもの
  5. 2 段目で、索引が問い合わせに解決しなかった行(解決先の決まらないテンプレートの呼び出し、索引に無い一致、C/C++ でないファイル)の節だけを 60・25・10・5・2 行に減らしたもの(`--other-limit`)。解決済みの呼び出し・参照・定義は減らしません
  6. 2 段目で、1 節に並べる行を 60・25・10・5・2 行に減らしたもの(呼び出し側が渡した `limit` より小さい値だけ)
  - **漏れのない一覧のファイル**: 結果に 1 行ずつ並べきれなかった行があるとき(上の出し直しをしたとき、文字列の中の一致が多くて件数にまとめたとき、修飾名で問うて別の記号に解決された行があるとき)は、**結果に並べなかった行だけ**を 1 行ずつ並べた一覧(`ltq refs --all` と同じ形)を、作業ツリーの中の `refs\<名前>-<ハッシュ>.txt`(場所は下)に書き、結果の最後の行で知らせます。関数の名前や引数を変えるときに、上書きの残り・無効な `#if` の中・C/C++ 以外のファイル・別の記号に解決された行まで、直す先を落とさないためです。結果と一覧を合わせると、名前を含む行がどれも 1 回ずつ出ます(一覧の最後の行が `== coverage: N lines here + M in the refs result = all ...`)。結果に出た行を一覧でもう一度読ませません。全部並んでいるとき(最後の行が `== coverage: all N lines ...`)は書きません。一覧のファイルには、サーバーの注記(プラグインより古い ltidx の知らせなど)を入れません(呼び出しのたびに中身が変わらないように)。開けなかったファイルがあるときは、結果にも一覧にも `== not searched:` の行が出ます(`../query/README.md`)
    - **一覧は、エージェントが 1 回で読める大きさのファイルに分けます**。Copilot CLI の `view` は、20 KB を超えるファイルを「File too large to read at once」と断ります(1.0.109 で、20,460 バイトは読め、24,555 バイトは断られた【実測】)。断られたエージェントはソースを grep し直し、往復が積み上がります(UE5 の `FAnimNode_Base::Update_AnyThread` で、一覧 37 KB が読めず、入力が cxxref なしより多くなった)。そこで、問い合わせの記号に結び付いた行(上書きの残り、呼び出し、無効な `#if` の中の行など)は 18,000 バイト以下のファイル(`<名前>-<ハッシュ>.txt`、複数なら `.1.txt`〜`.3.txt`)に分け、最後の行で `read it whole in one call`(複数なら `to read whole, one call each, in parallel`)と知らせます。節の途中で分けたときは、次のファイルの頭に見出しを `(continued)` 付きで繰り返します
    - 名前を含むだけの行(索引に無いテキストの一致、同じ名前の別の記号の行)と、3 つに収まらなかった分は、1 つのファイルにまとめます。18,000 バイト以下なら、次の番号のファイル(`.2.txt`〜`.4.txt`)として同じく丸ごと読ませます。超えるときは `.more.txt` に書き、`too large to read whole; search it with grep, or pass path to list one folder` と知らせます(UE5 の `Initialize` のような名前では 6 MB になります。読ませません)
    - 置き場所は、エージェントが読める所(作業ツリーの中)で、かつ rg や次の `refs` に当たらない所(`.` で始まるフォルダの中)です。索引がルートの下の隠しフォルダ(既定の `<ルート>\.index`)にあれば `<索引のフォルダ>\refs`、そうでなければ(索引がルートの外や、`.` で始まらないフォルダにあるとき)`<ルート>\.cxxref\refs` です。`.cxxref` には、中身を全部無視する `.gitignore` を置くので、git の変更には出ません
    - どちらにも書けないときだけ、一時フォルダ(`%TEMP%\cxxref-refs`)に書きます。このときは最後の行に `it is outside the workspace: if you cannot read it, pass path to list one folder at a time` と添えます(作業ツリーの外を読めないエージェントは、`path` でフォルダごとに引き直します)
    - 同じ問い合わせ(ルート・索引・名前・`path`・`exclude` が同じ)で、結果に並べた行も同じなら、同じファイルに書きます。中身が前と同じなら書き直しません(更新日時だけを新しくします)。結果に並べた行が違うとき(上限や `limit` が違って、別の形で返したとき)は、別のファイルです。同じサーバーを複数のエージェントが使っても、ほかのエージェントが受け取った結果と対になる一覧を書き換えません。7 日より古い一覧と、新しい順で 200 個を超えた分は、次に書くときに消します
  - 省いた行は、どれもフォルダごとか上の階層ごとの件数でも残ります。引数 `path` にそのフォルダを渡すと、1 行ずつ出し直せます。O3DE で、よくある名前(`Create`・`GetName`・`Activate` など)を引いても、3. で収まります【実測】
  - Copilot CLI は、ツールの結果が上限(既定は 20,480 バイト、環境変数 `COPILOT_LARGE_OUTPUT_THRESHOLD_BYTES`)を超えると、中身をモデルに渡さず、ファイルに退かせて先頭だけを見せます。大きなコードベースでよくある名前を引くと 75〜110 KB になり、答えの要の部分が届かなかったので、上限を設けました(`../docs/design.md` の「測り直し」)

## 索引の自動更新

コードを変えた後に `index-project.bat -Update` を手で実行する必要はありません。`refs` か `check` が呼ばれるたびに、索引の後に変わったソースがあるかを確かめ、あれば次のように作り直します(`autoupdate.py`)。

1. 裏で作り直しを始めます。ふだんは変わったファイルを読む TU だけを `ltidx -update` で解析し直します。新しいソースや消えた TU があるときは、`compile_commands.json` もソリューションや CMake から作り直します。最低優先度で、同時に 1 つだけ走ります
2. 最大 10 秒、終わるのを待ちます。終われば新しい索引で答え、出力の先頭に `auto-update: rebuilt the index ...` と出します
3. 終わらなければ、今の索引(変わったファイルの行は付け直したもの)で答え、`auto-update: rebuilding the index in the background ...` と出します。次の呼び出しから新しい索引を使います

実測では、ふつうの .cpp を変えたときは 0.5 秒、clang のヘッダーを読む重い .cpp を変えたときは 3.9 秒で、作り直してから答えました。多くの TU が読むヘッダーを変えると全体の作り直しに近い時間(コードベース A で 90〜120 秒)がかかるので、そのときは裏で続けます。

- **前提**: 索引を `..\scripts\index-project.bat` で作ったこと。作り方を `<索引>.tsv.recipe.json` に残し、それを使って作り直します。この機能より前に作った索引では、一度だけ `index-project.bat` を実行し直してください(それまでは `auto-update: off for this index` と出ます)
- **失敗したとき**: `auto-update: rebuild failed` と出し、今の索引で答えます。ログは `.index\update.log` にあります。次にソースが変わるまでは、同じ作り直しを繰り返しません
- **止めるとき**: 裏で CPU を使われたくない大きなコードベースでは、登録に `--no-auto-update` を足します。待たずにすぐ答えさせるなら `--auto-update-wait 0` です

  ```bat
  copilot mcp add code-ref-index -- python -I <このリポジトリ>\mcp\server.py --no-auto-update
  ```

- **判定**: ファイルの更新日時が索引より新しいかで決めます。`.vcxproj` のコンパイルの設定だけを変えた(ソースは変えていない)ときは気づかないので、`index-project.bat -Update` を手で実行します
- **待つ時間の上限**: Copilot CLI はサーバーごとにツール呼び出しの待ち時間を設定できます(`copilot mcp add --timeout <ms>`)。既定値は公式の文書で見つけられませんでした。既定の 10 秒は、他の Copilot クライアントで報告されている上限(Eclipse 版の 60 秒)より十分短くしてあります【既報】

## 呼び出しをまたいで保つもの

大きなコードベースで 1 回の `refs` を速くするため、サーバーは次の 3 つを呼び出しの間で保ちます。どれも結果を変えません(保たない動き `--no-resident` と一字一句同じになることを、テストと 5 つのコードベースで確かめています。O3DE では 37 個の名前・74 回の呼び出しで同じで、1 回は中央値 2.91 秒 → 0.52 秒でした【実測】)。

| 保つもの | 何を省くか | 置き場所 |
|---|---|---|
| ソースの一覧 | 呼ぶたびのソースの走査(UE5 の 20 万ファイルで 2 秒)。最初に 1 回だけ走査し、その後は Windows のファイルの変更の知らせ(`ReadDirectoryChangesW`)で追います。C/C++ 以外のファイル(テキストで名前を探すもの)の一覧も一緒に追います | メモリ |
| 単語のフィルタ | テキスト検索で、名前の単語を含まないと分かっているファイルを読まない(UE5 で 9〜16 秒 → 1〜4 秒)。C/C++ 以外のファイルにも別に持ちます | `<索引>.tsv.words.cache`・`<索引>.tsv.words-other.cache` |
| 名前の目次 | 索引の本体を頭から探さない。記号の最後の部分のハッシュから行の位置を引く(UE5 の 10 GB の索引で 8 秒 → 0.1 秒)。索引の差分(`.alt.tsv`)は小さいので、目次を作らずに頭から探します | `<索引>.tsv.names.cache` |

- **変更の知らせを確実に当てる**: 知らせは少し遅れて届くので、呼ばれるたびに `<ルート>\.index` に印のファイル(`.cxxref-watch-*`)を作ってすぐ消し、その知らせが届くまで待ってから一覧に当てます(知らせは起きた順に届くので、印より前の変更はすべて届いています)。`<ルート>\.index` が無い・書けない・2 秒待っても届かない・知らせがあふれたときは、前と同じく全体を走査します
- **監視の間はルートのフォルダを開いたままにします**: サーバーが動いている間は、ルートのフォルダの名前を変えたり消したりできません(中のファイルは自由に変えられます)
- **作るのは初めの 1 回**: 目次とフィルタは、無ければ最初の呼び出しで作ります(UE5 で目次 6.5 秒、フィルタはテキスト検索の 1 回分ほど)。目次は索引が変わったら作り直し、フィルタは更新日時の変わったファイルだけを読み直します。CPU のコアの数(最大 16)だけプロセスを分けて作ります。フィルタの形を変えたとき(今は版 4)は、前の版のフィルタを最初の呼び出しで作り直します(UE5 で、2 つ合わせて 293 秒)
- **大きさ**: UE5 で、目次 300 MB(索引の 3%)、フィルタ 192 MB(ソース 95 MB、C/C++ 以外のファイル 97 MB)。サーバーの専用のメモリは 0.27 GB から 0.8 GB 前後に増えます
- **大きなファイルが多いとき**: C/C++ 以外のファイルで、名前を含みうるファイルの合計が 1 GiB 以上のときは、その呼び出しの間だけプロセスを分けて探します(最大 8。プロセスを起こせないとき・途中で落ちたときだけ、スレッドで読み直します。探す処理そのものの誤りは、読み直さずにエラーで返します)
- **速さ**: UE5 で、温まった後の 1 回が 30 秒 → 6.7〜8.2 秒、19.5 秒 → 1.6 秒。サーバーを起動し直した後の 1 回目は 12.5 秒です。C/C++ 以外のファイルを大きさで除かなくなった後の値で、`Initialize` を含む翻訳のファイル 5.3 GB も読みます(除いていたときは 6.6 秒・1.8 秒・8.5 秒。`../docs/design.md` の「呼び出しをまたいで保つ」)
- 消しても、次の呼び出しで作り直します

## Copilot CLI で使う

チームで使うときは、このリポジトリをプラグインとして入れると、登録と使い方の指示が要りません(`../README.md` の「チームで使う」)。以下は手で登録するときの方法です。

すべてのプロジェクトで使う(ユーザー設定 `~/.copilot/mcp-config.json` に登録。`../scripts/register-copilot.bat` が同じことをします):

```bat
copilot mcp add code-ref-index -- python -I <このリポジトリ>\mcp\server.py
```

`.index` の無いプロジェクトでは、ツールは「索引が無い」と返すだけです。

プロジェクトごとに使う場合は、そのプロジェクトの `.mcp.json`(または `.github/mcp.json`)に書きます。ただし、Copilot CLI がこのファイルを読むのは**信頼済みのフォルダだけ**です。非対話モード(`copilot -p`)では `--trust-folder` を付けるか、事前に信頼しておきます【公式: docs.github.com の Copilot CLI「Add MCP servers」】。

```json
{
  "mcpServers": {
    "code-ref-index": {
      "type": "local",
      "command": "python",
      "args": ["-I", "<このリポジトリ>\\mcp\\server.py"],
      "tools": ["*"]
    }
  }
}
```

- ツールの名前は `code-ref-index-refs` と `code-ref-index-check` になります
- 非対話モードで承認するには `--allow-tool code-ref-index` を付けます。`--available-tools` で絞るときも `code-ref-index` を入れます
- サーバーのパスは各自の環境のものなので、リポジトリにコミットする `.mcp.json` には向きません。ユーザー設定に登録するほうが手軽です

### 使い方の指示

Copilot CLI は、許可リストに無い MCP サーバーの初期化時の説明(instructions)をシステムプロンプトに入れません。それでも計測では、指示なしで 12 回とも `refs` が最初に使われました(正答 11/12)。指示を足すと 12/12 になり、トークンも減りました(`../docs/design.md`)。指示を入れるなら、`../scripts/setup-instructions.bat`(プラグインの拡張なら `/cxxref-enable on`)で、`../scripts/cxxref-instructions.md` の内容を自分の手元だけか、プロジェクトの `.github/copilot-instructions.md` に足します。

## テスト

`test\run_test.bat` をダブルクリックします。`server.py` を子プロセスで起動し、合成した小さな索引に対して `initialize`・`tools/list`・`tools/call`(`refs`・`check`)と誤った要求を JSON-RPC で送り、返事を確かめます。結果の大きさの上限(短い形で収まればそれを返すこと、解決済みの行が多いときは節ごとの行数を減らし、後ろの節を切らないこと、収まらなければ切ること、環境変数 `CRI_MAX_OUTPUT_BYTES`、0 なら切らないこと)と、並べきれなかったときに漏れのない一覧のファイルを書くこと(置き場所・同じ中身を書き直さないこと・数の上限)も確かめます。Copilot は要りません。

`ltidx.exe` をビルド済みなら、自動更新も確かめます(`test_autoupdate.py`)。小さなプロジェクトを索引にしてからソースを変え、次の呼び出しで作り直されること、TU を足すと拾うこと、待たない設定でも次の呼び出しで新しい索引を使うこと、記録の無い索引には触らないこと、失敗を繰り返さないことです。GitHub Actions では、ltidx をビルドするジョブでこれを流します(`CRI_REQUIRE_LTIDX=1` を付け、`ltidx.exe` が無ければ飛ばさずに失敗させます)。

## 制約

- 呼び出しをまたいで保つものの限り:
  - ネットワークドライブでは変更の知らせが使えないことがあり、そのときは呼ばれるたびに全体を走査します(結果は同じで、速くならないだけ)
  - `PROGRA~1` のような 8.3 形式の短い名前に見えるフォルダ名(`backup~1` など)の知らせが来ると、念のため全体を走査し直します(性能だけ)
  - 索引の後に変わったファイルの行は、名前の目次ではなく索引の本体を 1 周して拾います(O3DE の 900 MB で 0.8 秒)。変わったファイルが無いときの速さが、上の値です

- 最後に引いた索引を開いたまま保ち、索引のファイル(本体と `.tu.tsv`・`.skip.tsv`・`.deps.tsv`)の大きさと更新日時が変わらない間は使い回します。ソースの一覧は、下の「呼び出しをまたいで保つもの」で変更の知らせから保ちます(`--no-resident` では呼ばれるたびに走査し直します)。鮮度の確認(索引の後に変わったファイル)は、呼ばれるたびにやり直します。常駐中に索引を作り直しても、次の呼び出しから新しい索引を使います
- 結果が大きくて短い形(`--compact`)で出し直すときは、同じ呼び出しの中の索引の検索とテキスト検索の結果を使い回します
- TU が読んだファイルの一覧(`.deps.tsv` の 2 列目)を、`.index\<索引>.tsv.seen.cache` に書き残します。`.deps.tsv` の大きさと更新日時が同じ間は、`.deps.tsv`(UE5 で 6.7 GB)を読まずにこれを使います。書けないフォルダでは書かずに続けます
- Unreal Engine 5(索引 10 GB、ソース 20 万ファイル)では、1 回の `refs` が 43〜91 秒から 19〜33 秒になりました(サーバーを立ち上げ直した後の 1 回目から。結果は前と同じ)。その後、上の「呼び出しをまたいで保つもの」で、温まった後の 1 回が 1.8〜6.6 秒、起動し直した後の 1 回目が 8.5 秒になりました。C/C++ 以外のファイルを大きさで除かなくなった今は、1.6〜8.2 秒と 12.5 秒です(`../docs/design.md` の「Unreal Engine 5 での計測」)
- 自動更新は `.index` の中に `update.lock`(作り直し中だけ)・`update.json`(前回の結果)・`update.log` を置きます
- MCP の stdio トランスポートの、ツールに要る範囲(`initialize`・`tools/list`・`tools/call`・`ping`)だけを実装しています
