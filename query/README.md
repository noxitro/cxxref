# ltq — ltidx 索引の問い合わせ CLI

## 目的

ltidx が作った C++ の参照索引(TSV)を引き、エージェントが 1 回の実行で答えを出せる形で返します。
段階 1 では、エージェントが索引を rg で引いていました。そのときに残った誤答のうち、次の 2 つをツールの側で防ぎます。

- テンプレート内の未解決の呼び出し(`dep` 行)を引き忘れる・件数上限で切り捨てる → `refs` が同じ名前の `dep` 行を必ず一緒に返す
- ソースを rg で「確認」して、コメント内の一致を答えに足す → `refs` がソースの同名の一致を自分で集め、索引に無いものの理由(コメント内・無効な `#if` など)を添える

設計の背景と計測結果は `../docs/design.md` を参照してください。Copilot から使うときは、シェルの要らない `../mcp` の MCP サーバーを勧めます(中身は同じです)。

## 前提

- Python 3.10 以降(標準ライブラリだけを使います)
- `../indexer` の ltidx で作った索引一式。`<索引>.tsv` と、同じ場所の `.tu.tsv`・`.skip.tsv`(コメントと無効な `#if` の範囲)。`../scripts/index-project.bat` が `<ルート>\.index\index.tsv` に作ります。構成(Debug/Release、プラットフォームなど)ごとに `-Name` を変えて作ると、`.index\<名前>.tsv` が並びます
- ltq は、`.deps.tsv` から作った「TU が読んだファイルの一覧」を、同じ場所の `<索引>.tsv.seen.cache` に書き残します。`.deps.tsv` の大きさと更新日時が同じ間はこれを読みます(大きな索引で数十秒かかる読み込みを省くため)。消しても、次の問い合わせで作り直します

## 起動

`ltq.cmd` を PATH の通ったフォルダに置くか、フルパスで呼びます。ソースのルート(索引のパスの起点)で実行します。`--root` を省くと、カレントフォルダから親へさかのぼって `.index` のある最初のフォルダをルートにするので、ルートより下のフォルダで実行しても使えます(そのときは出力の先頭に `root: ...` と出ます)。索引の既定は `.index` の中の索引本体(`.tu.tsv`・`.skip.tsv` 以外の `.tsv`)すべてで、構成をまとめて引きます。`--index` を繰り返して指定することもできます。

```bat
ltq refs nox::io::File::Read
ltq check runtime/kernel/delegate.h:434 runtime/core/world.cpp:297
ltq --index D:\idx\game.tsv --root D:\src\game refs Renderer::Draw
```

コマンドラインのツールなので、ダブルクリックでは使いません。

## 使い方

- `ltq refs <名前>` … 修飾名か、その末尾(`File::Read`)を渡します。出力の節は次のとおりです
  - `calls`: clang が解決した呼び出し。`[in 関数]` は、その呼び出しが書かれている関数です。`call-using` は、テンプレート内の `using Base::f;` を経由した呼び出しを、実体化から引いた宣言の先で解決したものです
  - `other references`: 関数ポインターの取得、テンプレート引数など
  - `definitions and declarations`: 定義と宣言
  - `virtual dispatch`: 問い合わせが仮想関数のときだけ出ます
    - 問い合わせが上書きしている基底のメソッドと、その呼び出し。基底のポインタや参照越しの呼び出しは clang が基底のメソッドに解決するので `calls` には入りませんが、実行時の型によっては問い合わせの関数が走ります
    - 問い合わせを上書きしているメソッドと、その場所。それらに解決された呼び出しの数も添えます(上書きした側を呼ぶもので、問い合わせは呼びません)
  - `unresolved template calls (dep)`: テンプレート内で解決先が決まらない、同じ名前の呼び出し。実体化で別の記号に解決されている位置には、その解決先を添えます
  - `text matches ... not in the index`: ソースの同じ単語の一致のうち、索引に同名の行が無いもの。理由ごとに分けます(コメント内・無効な `#if`・マクロ定義・文字列・どの TU も含まないファイル・その他)。件数の多い分類はディレクトリごとにまとめます
    - どの TU も含まないファイル(別プラットフォーム向けのコードなど)と「その他」の一致には、索引の中に同じ形の呼び出しがあれば、clang がそれを何に解決したかを添えます。同じ文面の行なら `(the same line text elsewhere ...)`、文面は違うが受け手の式(`g->` など)が同じなら、弱い手がかりとして `` (`g->CreateTexture` elsewhere resolves to ... ; check the receiver type) `` です。解決先が 1 つに揃うときだけ出し、手がかりの付いた行はディレクトリごとにまとめずに出します
    - 分類に、`dropped`(マクロの展開がコードとして残さない引数。無効にした assert やログ、`#`・`##`)、`local`(同じ名前の関数の中の変数・引数・テンプレートの引数)、`directive`(`#pragma`・`#include`・`#error` の行)があります。`dropped` は `inactive` と同じく、そのファイルを読んだすべての構成で捨てられているときだけそう分類します
  - マクロの名前で問うと(`ltq refs NOX_ASSERT`)、`#define` を定義の節に、展開(名前が書かれた場所)を `macro expansions` の節に、`#ifdef`・`defined()`・`#undef` をそれ以外の参照の節に出します
  - 名前を置き換えるマクロ(`windows.h` の `#define GetMessage GetMessageW`)があると、`Mail::GetMessage` のように問われても記号は `Mail::GetMessageW` です。そのときは置き換え後の記号を答え、`the macro GetMessage renames it to Mail::GetMessageW` と添えます
  - `other symbols named ...`: 同じ短い名前の別の記号と件数
  - `--limit N` で 1 節の上限(既定 200)、`--exclude <ディレクトリ名か相対パス>` でテキスト検索から外す場所を指定します
- `ltq refs <名前> --compact` … 短い形です。呼び出しと「probably a call」の一致はすべて出し、報告しない一致(コメント内・無効な `#if`・文字列・マクロ定義)はフォルダごとの件数に、別の記号に解決されたテンプレートの呼び出しと「probably not the query」の一致は件数にまとめます。MCP サーバーは、結果がクライアントの上限を超えそうなときにこれを使います
  - 修飾名(`ns::File::Read` など)で問うと、無効な `#if` の中でも末尾の 2 つ(`File::Read`)がそのまま書かれた行は件数にまとめずに出します(別の構成でだけ使われる呼び出しが消えないように)
  - フォルダごとの件数は、多い順に 10 フォルダまで(報告しない分類は 5 まで)出し、残りは「... N more folders (M matches)」の 1 行にします
- `ltq check <path:line[:col]> ...` … その行にある索引の行と、その行を含むコメント・無効な `#if` の範囲を返します
- 出力の先頭には、索引の作成日時と、解析にエラーがあった TU を必ず出します
  - 解析にエラーがあった TU・変わったファイル・増えたソースは、問い合わせの名前を含むファイルの分だけを並べ、残りは件数にします(`refs` は名前を含むファイルと結果のあるファイル、修飾名なら修飾名を書いたファイルと結果のあるファイル。`check` は問われたファイル)。結果の行はどれもそのファイルにあるので、残りは結果に関わりません
- 構成が複数あるときは、行を和集合にします。そのファイルを読んだ構成の一部にしか無い行には `[only in <構成名>]` を付けます。無効な `#if` は、そのファイルを読んだすべての構成で無効なときだけ「無効」と分類します
- 鮮度: 索引の後に変わったファイル・増えたソース・消えた TU を、出力の先頭に出します
  - 変わったファイルの行は、索引にあるソース行の文字列を今のファイルから探して付け直します(`[moved from line N]`)。行の中身が変わっていたら、近くの変わっていない行のずれから推定します(`[line changed after indexing; estimated from line N]`)。コメントと無効な `#if` の範囲も同じだけ動かします
  - 行の順序は保たれるとみなすので、関数を入れ替えるような編集では推定になります。正確な結果には索引を作り直してください
  - テキスト一致の行には、従来どおり `[file changed after indexing]` を付けます
  - 索引を正確にするには、`../scripts/index-project.bat` に `-Update` を付けて、変わった TU だけを作り直します
  - 「読んだファイル」は、ltidx が記録した TU ごとの読んだファイル(`.deps.tsv`)で判定します。`.deps.tsv` の無い古い索引では、参照もコメントも無いヘッダーを「どの構成も読んでいない新しいファイル」と見誤ることがあります
- 文字コード: ltidx は UTF-8 として正しくないソース(Shift_JIS など)を UTF-8 に直して解析し、列番号もその後のバイト位置で記録します。ltq もテキスト検索と行の付け直しの前に同じ変換をします。コードページは、ltidx が TU ごとに記録したもののうち最も多いものです
- 出力の見出しは英語です。読み手がエージェントなので短くし、コンソールの文字コードの違いで見出しが化けないようにしています

## 制約

- テキスト検索はルート配下の C/C++ と Objective-C/C++ のソース(`.h` `.cpp` `.inl` `.mm` など)を毎回読み、索引も毎回読みます。1 回の問い合わせは、コードベース B(約 1,000 ファイル)で 0.2〜0.4 秒、その写しを 20 個並べた合成のコード(約 2 万ファイル、索引 480 MB)で 1.9〜4.6 秒です(`../docs/design.md` の「大規模なコードでの速さ」)
- 文字列リテラルとマクロ定義の判定は、その行の字句だけを見た簡易なものです(生文字列リテラルは見分けません)
- 無効な `#if` の範囲は、索引を作った構成のものです。別の構成で有効になる分岐は、その構成の索引を足すまで索引に入りません

## テスト

`test\run_test.bat` をダブルクリックします(合成した小さな索引で、構成の統合・行の付け直し・鮮度の表示・仮想関数の上書き・Shift_JIS のソース・短い形(`--compact`)・一致のあったファイルが多いときの範囲の読み方を確かめます。LLVM は要りません)。リポジトリのルートの `run-tests.bat` は、ほかのテストもまとめて流します。
